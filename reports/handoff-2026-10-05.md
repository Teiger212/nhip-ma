## How we work (also in memory)

- **The cycle:** grill → amend PRODUCT.md and the ADRs → spec in the epic or ticket → tickets as sub-issues → build.
- **Building:** each ticket is one Opus agent in its own worktree (`isolation: "worktree"`).
  - Red first: the `test-author` E2E or a Vitest, seen failing before behaviour code.
  - A fresh review before merge.
  - No Claude attribution anywhere.
- **Subagents:** a ticket agent may spawn its own (test-author, Explore, a reviewer, parallel workers). Pick the model per task: Opus for build and review, Fable for the hardest reasoning, Sonnet for mid-weight work, Haiku for mechanical lookups. Default to Opus when choosing isn't worth it.
- **Code:** async/await, not `.then`/`.catch` chains. A chain is allowed only to start a race in a test, with a comment saying why. zod's `.catch()` is schema API and fine.
- **Never:** port 3010 (Eyal's dev server), the main dev DB `supastarter`, a hand-edited `pnpm-lock.yaml` (take main's, then `pnpm install`), or a printed `.env`.
- **Merging:** Eyal merges. Check `gh pr view <n> --json state` before saying a PR awaits merge.
